# Open Questions

This document exists so nothing here gets quietly treated as settled just because it's documented elsewhere in detail. Everything below is a real gap, not a formality — most of it is carried forward directly from the source spec's own Section 20 ("What Is Still Open"), written before any of this was built, and this build has not closed most of it.

## The one thing that isn't a design problem (Section 20.1)

The source spec is direct about this: whether a family actually sets this tool up *before* a crisis, rather than only discovering it during one, is the single largest unresolved risk in the whole idea — raised three separate times across the earlier ideation process without ever being closed, because **it cannot be closed by more design or engineering work**. Building the onboarding flow well is not evidence that families would use it.

**This build has not touched this question at all.** Nothing here — the tiering accuracy, the test coverage, the safety guarantees — is evidence toward it either way, because none of it addresses distribution or real-world adoption. The spec's own recommended next step stands unchanged: a real conversation with someone who has dealt with a PMJAY denial, or an ASHA worker who could plausibly introduce this tool, asking directly whether they'd have set it up in advance if offered — *before* more build time is spent, not after. A ready-to-use guide for exactly that conversation — extracted from the source spec's Section 33 and Section 70 into one standalone document — is at [`docs/VALIDATION_INTERVIEW_GUIDE.md`](VALIDATION_INTERVIEW_GUIDE.md). `docs/TESTING.md` formalizes this as hypothesis H5 and, following the spec's own prioritization, flags it as the cheapest of the five validation hypotheses to test and the one that changes the most downstream if it fails — meaning it should be tested first if this moves forward, not last.

## Diligence gaps, carried forward honestly (Section 20.2)

The spec names these itself rather than implying a more thorough search happened:

- The competitor check was run twice, targeted at this specific idea — reasonable for the pace of the original ideation process, not an exhaustive search. A deeper pass (recent accelerator cohorts, government innovation-challenge winners — the spec specifically flags the "Ayushman Bharat PMJAY Start-Up Grand Challenge" as surfaced but not followed up on for past winners — and direct app-store listings) would strengthen confidence.
- No hard frequency statistic exists for how often a real family encounters a wrongful denial. The evidence behind this idea is qualitative (real documented cases) and structural (a named, tracked national grievance category), not a quantified rate. This is also H1 in `docs/TESTING.md`, and is not code-testable for the same reason.

## Build-time risk retrospective (Section 20.3): did this build avoid the trap it warned about?

The spec flagged, in advance, that the single easiest mistake during build would be drifting toward a flat, lookup-style version of this idea under time pressure — since that version is genuinely simpler to build than the real, ambiguity-handling one (Section 8 draws this line explicitly). It's fair to check the actual code against that warning rather than just note the warning existed:

- Retrieval is a keyword pre-filter, not the final answer — `internal/retrieval` explicitly hands off to an LLM extraction step rather than returning a match directly (see `../ARCHITECTURE.md`).
- The pending-vs-denied distinction — the spec's own named example of what a lookup tool cannot do — is implemented as a real cross-check between an LLM signal and an independent deterministic pattern detector (`docs/SAFETY_DESIGN.md` §5), not a keyword match on the word "pending."
- The confidence-gap rule and the amber tier as a whole exist specifically so the system can say "genuinely unresolved" instead of forcing every case into a binary yes/no — the opposite of what a flat lookup would do.

This is a reasonable case that the build stayed on the correct side of the line the spec worried about. It is **not** independent confirmation — it's a self-assessment against the spec's own stated criteria, not an outside review, and should be read with that caveat rather than as a settled verdict.

## What was deliberately not built

From `../ARCHITECTURE.md`, matching the source spec's Section 15.5 and Section 16:

1. **Full HBP coverage.** The real master list is ~1,900 procedure codes. This build now ships 315 packages, 300 of them verified directly against government-published HBP rate schedules (up from 274/289, 40/24, and 1 in the three sessions before this one) — see `docs/DATA_SOURCES.md` for exactly which records are real, which are still placeholder, and why. That's a real jump — General Medicine and Pediatric per-diem admissions and Medical Oncology are now genuinely covered, including 26 previously-unreachable General Medicine records this session picked up — but still a fraction of ~1,900, and four separate fetch attempts across three sessions and three different source documents/domains hit the same kind of hard extraction wall before reaching the same seven specialties: General Surgery, Orthopaedics, Obstetrics & Gynaecology, Ophthalmology, ENT, Urology, Neurosurgery. Full extraction remains real, unfinished work, just a smaller and more specific remainder than before — and this session found a specific, concrete lead on where to look next (see `docs/DATA_SOURCES.md`'s 19 August section) rather than a dead end. The rate-currency question (HBP 2.1 vs. HBP 2022) flagged in the previous version of this document is now resolved — see the same file.
2. **Live PMJAY pre-authorisation status checking.** No public API exists for this today.
3. **Automated CGRMS complaint submission.** The system drafts the complaint text and — since this session — renders it as part of a real, formatted, downloadable/printable PDF (`internal/document`, `GET /api/v1/cases/{id}/document`) rather than only an on-screen text box. That's a genuine step toward "ready to actually hand to someone," but it does not close this gap: the family still submits the draft themselves, through the official Ayushman App or whichever channel they choose. Automating the submission itself would still need an integration that doesn't currently exist.
4. **Live NALSA case-routing integration.** The handoff panel gives the real, verified toll-free number (15100) and a prepared case summary — not an API-level handoff to an actual Para Legal Volunteer queue.
5. **A no-install distribution channel (e.g. WhatsApp).** This build is a web app only. The source spec's own Appendix Q sketches the roadmap case for this, relevant given the named user (Section 5) may not reliably have a smartphone with spare storage for another installed app.
6. **Malayalam localization of the response templates.** The extraction step already understands Malayalam/English code-mixed *input* natively — that's genuinely one of the three reasons (Section 8) this isn't just a lookup tool. But the hard-coded response *templates* a family actually reads (`internal/response/templates.go`) are English-only, deliberately not machine-translated without native-speaker review for safety-critical, medical/legal-adjacent text. Full reasoning in `docs/DATA_SOURCES.md`.
7. **Screen-reader accessibility of the generated PDF (`internal/document`).** The web result page takes this seriously — `role="alert"` on the care-first banner, color never used alone to convey an outcome (see `docs/TESTING.md`'s `TierBadge` coverage) — and the PDF is not held to that same bar yet. It's an untagged PDF: no `/StructTreeRoot`, no marked content, no reading-order metadata — visually laid out correctly (verified — see `internal/document/README.md`), but a screen reader has no structural information to work with beyond raw text-positioning operators, which is a meaningfully worse experience than the actual web page gives an assistive-technology user today. Proper PDF tagging is a real, substantially larger undertaking than generating the visual layout was (it needs an explicit structure tree matching the reading order, not just correctly-positioned text), and wasn't attempted this session. Separately, the choice to open the PDF `inline` in the browser's own viewer (see `handleGetCaseDocument`'s doc comment in `internal/api/handlers.go`) was reasoned through for mobile-friendliness but not verified against a real Android/iOS device in this sandbox — the same category of honestly-stated limitation as the missing Playwright coverage above, not silently assumed to be fine.

## Testing gaps

Covered in full in `docs/TESTING.md`, summarized here:

- **H1, H2, H5** (is the problem common enough at the individual level; does the tool change behavior, not just understanding; do families set it up before a crisis) are field-study-level hypotheses that no amount of unit testing can answer. Nothing in this codebase should be read as evidence toward any of the three.
- **H3** (tiered logic accuracy) has real automated coverage via the three-arm test structure, but only against a hand-constructed case bank — not against the full space of how real families will actually phrase real situations.
- **The backend test suite grew from 185 to 235 tests this session** (all packages, race-detector clean), entirely from the security/reliability hardening pass — not new business logic. New coverage: the rate-limiter IP-spoofing fix (6 tests, including one that directly proves the spoof no longer works), request body size limits (3 tests), and retry/backoff logic for the Anthropic API call (10 tests covering every retry path — success-after-retry, exhaustion, non-retryable-fails-fast, context-cancelled-mid-backoff). See `docs/TESTING.md` for the full per-package breakdown.
- **The frontend test suite now covers every component** — 74 tests across 12 files (Vitest + React Testing Library), up from 35/5, then 66/11 as of the previous session. This session's addition (`CaseDocumentPanel`, the new "download this case as one document" button — see item 3 under "What was deliberately not built," above) has its own component tests plus a dedicated page-level integration assertion that the correct case ID actually reaches it, not just that it renders without crashing. The five components that had no dedicated coverage as of two sessions ago (`TierPanel`, `ActionSteps`, `HandoffPanel`, `CopyableTextBox`, `Header`) still do, and `app/case/[id]/page.test.tsx` renders the actual full page component tree against a mocked API boundary — loading/error/loaded states, every outcome's conditional panels, the care-first message's always-present guarantee at the page level, not just the component level. This is not a substitute for a real browser-driven end-to-end test (Playwright): this sandbox's network allowlist doesn't reach a browser-binary CDN, so installing one wasn't possible, and that's a real, honestly-stated limitation, not a silently-dropped item. See `docs/TESTING.md` for the full breakdown and exactly what the integration test does and doesn't cover.

## If only one of these gets addressed next

Following the spec's own explicit prioritization: **talk to a real family or ASHA worker about Section 20.1 before writing more code.** [`docs/VALIDATION_INTERVIEW_GUIDE.md`](VALIDATION_INTERVIEW_GUIDE.md) has the actual questions to ask, ready to use. Every other item on this page is real, but none of them matters if the answer to "would anyone set this up before a crisis" turns out to be no — and that's the one question here that more engineering, more test coverage, or more documentation cannot answer.
