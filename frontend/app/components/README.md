# `frontend/app/components`

Every React component this frontend has, all client components (`"use client"` where they need interactivity; the presentational ones don't need the directive but are still only ever rendered from client or server components) except `icons.tsx`, which is not a component at all — see its own section below. Ten components live directly in this folder; a further seven, the marketing/content sections used across the five content pages, live in `components/landing/` (its own `README.md`) since they're a genuinely different cluster: no client-fetched data, no test files (see that README for why), reused across multiple pages rather than owned by one. None of the seventeen reach into global state or a shared store; everything is props in, JSX out, which is what makes each one independently unit-testable (see `docs/TESTING.md`).

## The ten components in this folder, grouped by what they're for

### Site chrome

- **`Header.tsx`** — the site navbar: brand link, desktop nav links to the four content pages (with `usePathname`-based active-state styling), a mobile hamburger menu (`useState` + `Escape`-to-close + auto-close on route change), and the PMJAY helpline (`tel:14555`) — the one helpline number reachable before a case even exists. A client component (it wasn't, before the navbar existed) — if you're adding a test that renders anything containing `Header` and mocks `next/navigation`, the mock needs a `usePathname` export or Header throws; see the comment in `app/case/[id]/page.test.tsx`'s mock for a worked example. Also exports `SHELL_WIDTH`, the `max-w-6xl` constant every page's `<main>` and `Footer` (`components/landing/Footer.tsx`) import so page chrome and content line up on the same edge.
- **`IntakeForm.tsx`** — the actual form, rendered on the home page. Three things worth knowing: (1) it duplicates the backend's 5-character minimum description length client-side, specifically to avoid a wasted, paid API round-trip on an obviously-too-short input — see `frontend/lib/README.md`'s note on this being a real, acknowledged drift risk, not a codegen-guaranteed invariant; (2) it renders `ApiError`'s `fallbackGuidance` field directly under the main error message when a submission fails, which is the frontend half of the backend's care-first-on-failure guarantee (see `backend/internal/api/README.md`'s `handleIntake`); (3) the three `EXAMPLE_PROMPTS` buttons exist specifically to lower the barrier for a family unsure how to phrase their situation — clicking one fills the textarea, it doesn't submit.

### The result page (rendered by `app/case/[id]/page.tsx` — see that folder's own `README.md` for how these compose)

- **`CareFirstBanner.tsx`** — the frontend's structural mirror of the backend's own unconditional care-first guarantee. Read its own header comment: the backend can never construct a `FamilyResponse` without a care-first message (enforced by the type system — see `backend/internal/response/README.md`), but a frontend bug could still render that message last, small, or easy to miss. This component exists so every case page renders through one single, consistent, `role="alert"` (announced by assistive technology, not just visually first) treatment, rather than each page remembering to build a care banner itself.
- **`TierBadge.tsx`** — one outcome → an icon, a label, and a short description, always together, never color alone (a real accessibility requirement, not a nice-to-have — a colorblind reader, or anyone on a low-quality screen, must still be able to tell green from red from the text and icon). `TIER_STYLES` is the map from `Outcome` (see `frontend/lib/README.md`) to its visual treatment — icon component, icon name (a stable string id, used by tests and never rendered as text), and the four `tier-*` token classes for that outcome. If you add a sixth outcome on the backend, this map needs a matching entry with a genuinely new `Icon`/`iconName` — the component's own test suite checks every outcome's icon is distinct from every other outcome's, by both identity and name, so a copy-pasted entry that reuses an existing icon fails loudly.
- **`TierPanel.tsx`** — composes `TierBadge` with the tier message and, when present, the citation ("Based on: ..."). The citation section is genuinely absent, not rendered empty, when there's nothing to cite (amber and handoff outcomes often have none — see `backend/internal/response/README.md`'s table of what's populated per outcome) — an empty "Based on:" with nothing after it would look like a bug, not an intentional omission.
- **`ActionSteps.tsx`** — the numbered "what to do right now" list. Renders nothing at all (not an empty section) for a zero-length array — a second, independent guard behind the page-level conditional that already checks `action_steps.length > 0` before even mounting this component, matching the defense-in-depth pattern `CareFirstBanner` uses.
- **`CopyableTextBox.tsx`** — the shared component behind both the hospital script and the draft complaint text boxes. One click copies the exact displayed text via `navigator.clipboard.writeText`, swaps the button to an icon + "Copied" confirmation for a few seconds, then reverts. If the Clipboard API rejects (older browsers, a denied permission), it degrades to the plain "Copy" state rather than throwing — the text is still fully readable and manually selectable in the box regardless, so a thrown, unhandled error here would be a strictly worse outcome than just not showing the confirmation. `aria-live="polite"` on the button means the state change is announced to assistive technology without needing focus to move.
- **`HandoffPanel.tsx`** — rendered only for the handoff outcome. States NALSA by name, states the help is free (deliberately — a family mid-billing-dispute is exactly the audience likely to wonder whether calling a number leads to another bill), and surfaces `tel:15100` — NALSA's real, verified toll-free number, distinct from Header's own `tel:14555` (the PMJAY scheme helpline, a different number for a different purpose). Also renders the case summary so the family doesn't have to re-explain their situation on the call — the frontend rendering of the same `handoffSummary` the backend built in `internal/response/generators.go` specifically so nothing has to be re-explained from scratch.
- **`CaseDocumentPanel.tsx`** — links to `GET /api/v1/cases/{id}/document` (`backend/internal/document`), the same case content rendered as one downloadable/printable PDF instead of the individual on-screen sections. A plain `<a target="_blank">`, not a fetch-and-save-blob click handler — see the component's own doc comment for why that's deliberate (the browser's native PDF viewer gives print/save/share for free, on both desktop and mobile, in a way a hand-rolled download flow wouldn't reliably match). Rendered unconditionally (every outcome gets a document, not just some), right after the tier/handoff panels and before the granular action-step/script/complaint sections — the idea being that a family in a hurry can grab the one document and go, without needing to have read every section on screen first.
- **`EvidenceForm.tsx`** — the staff-name/time/note capture form, shown at the point in the flow where it's still actionable (Green, Amber, Mixed — never Red or Handoff, mirroring `backend/internal/response`'s `evidencePrompt` gating exactly). At least one of the three fields is required — the same "don't submit nothing" rule the backend's `handleAddEvidence` enforces server-side too (see `backend/internal/api/README.md`), checked here first purely to save a round trip on an obviously-invalid submission.

## `icons.tsx`: the one shared, non-component file in this folder

Every icon anywhere in this frontend — landing page, tier badges, buttons, the FAQ chevron — is a small hand-drawn inline SVG exported from this one file, not an icon package. That's deliberate, matching the rest of the app: zero third-party UI dependencies (see `package.json` — there was no icon library installed before this file existed, and adding one just to render checkmarks and arrows would be the first UI dependency in the project for very little gain). Each export is a pure function of `{ className }` — no internal state, no conditional rendering, no accessibility semantics of its own. That last point is the reason `icons.tsx` doesn't have a matching `icons.test.tsx` alongside the ten components' tests below: accessibility (whether an icon is `aria-hidden` or carries a label) is entirely the calling component's responsibility and is already covered by that component's own tests (e.g. `TierBadge.test.tsx` asserting its icon wrapper is `aria-hidden`) — a test file for `icons.tsx` itself would only be asserting that each of ~20 near-identical wrapper functions returns an `<svg>`, which isn't meaningfully different from a type error the compiler already catches.

If you need a new icon, add it here rather than inline in a component — even a "one-off" icon tends not to stay one-off in a five-outcome, multi-page app, and a second hand-rolled checkmark elsewhere is exactly the kind of drift this file exists to prevent.



Data fetching happens exactly once, in `app/case/[id]/page.tsx` (client-side, via `lib/api.ts`'s `getCase`) or in `IntakeForm.tsx`'s own submit handler (via `createCase`). Every component in this folder is handed already-fetched data as props and renders it — no component here calls `fetch` itself except the two that own a real user action (`IntakeForm` submitting, `EvidenceForm` saving). This is what makes every component in this folder testable with React Testing Library alone (render with props, assert on output) rather than needing a mocked network layer in every single test file — the mocking only has to happen at the two real network-touching boundaries, and at the page level for the one genuine integration test (see `frontend/app/case/[id]/README.md`).

## If you're adding a new component

- Keep the "plain props in, JSX out" shape unless there's a specific reason not to (a genuine new network-touching action, following `IntakeForm`/`EvidenceForm`'s pattern).
- Give it a same-named `ComponentName.test.tsx` in this same folder — every one of the ten components here has one; a component without a test is the exception that needs justifying, not the default. (`icons.tsx` is the one deliberate exception in this folder, and it isn't a component — see its own section above for why. `components/landing/` is a different folder with its own, different, testing rationale — see its README.)
- If it renders an outcome-dependent color or icon, add to `TierBadge.tsx`'s `TIER_STYLES`, don't invent a second styling map elsewhere.
- If it needs an icon, add it to `icons.tsx` and import it — don't inline a new SVG or reach for an icon package.
- If it needs a status/category tag, use the `.badge` class (`app/globals.css`) plus color utilities — never `rounded-full` for that purpose. See `app/README.md`'s "Surfaces" section for the reasoning.
- This file is part of the codebase's documentation convention — see the repo root `README.md`. Keep it in sync with the code, in the same change.
