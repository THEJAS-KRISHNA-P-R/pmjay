# `cmd/server`

The binary entrypoint. `go build ./cmd/server` (or any of the `Makefile`'s `build-*` targets — see `backend/README.md`) produces the single static binary this whole backend ships as. `main.go` is short and stays that way on purpose: it wires real dependencies together and gets out of the way — the actual logic lives in `internal/`, not here.

## Files

`main.go` — `main()` sets up structured JSON logging, builds a `context.Context` that cancels on `SIGINT`/`SIGTERM` (via the standard library's `signal.NotifyContext`), and delegates to `run(ctx, logger)`, which does the real work and returns an error instead of calling `os.Exit` directly.

`main_test.go` — `run` taking `ctx` rather than listening for OS signals itself is what makes it directly unit-testable: a test cancels a context deterministically instead of needing to send a real signal to the whole test process. 10 tests, 97.3% coverage, covering every failure path deliberately — config errors, store-creation errors, server-bind errors, shutdown-timeout errors, and graceful shutdown on cancellation — plus `main()`'s own `os.Exit(1)` path, tested via the standard (and only correct) technique for anything that calls `os.Exit`: re-executing the test binary as a subprocess and checking its real exit code. (An earlier version of this file claimed `run` had no dedicated test and called that "a reasonable gap for a hackathon-stage wiring function" — that was true once, and is exactly the kind of claim this project's own culture exists to catch and correct rather than leave stale once it no longer is.)

## Startup sequence, and what each step's failure actually means

1. **`config.Load()`** — any error here (a malformed `RATE_LIMIT_PER_MINUTE`, an empty `PORT`, an `LLM_PROVIDER` that isn't `anthropic`/`groq`/`gemini`) is a deploy-time misconfiguration; the process exits immediately, before anything else has a chance to run. See `internal/config/README.md`.
2. **A missing API key for the active provider is logged as a `Warn`, not fatal** (`cfg.ActiveAPIKey()`/`ActiveAPIKeyEnvVar()` — see `internal/config/README.md`). The process continues starting. This is deliberate so the dataset, the health endpoint, and everything that doesn't need a live model can be verified independently of having a real key configured.
3. **`hbp.Load()`** — loads and validates the embedded dataset (see `internal/hbp/README.md`). A failure here means a genuinely malformed dataset made it into the binary; the process refuses to start rather than serve with data it can't trust. This is the one failure path in `run` that has no dedicated test in `main_test.go` — not an oversight, see that file's own comment: the embedded data is compiled in, not user-supplied, so making `hbp.Load()` fail from a test would mean editing the actual embedded source files and rebuilding, which isn't a legitimate per-test technique. `hbp`'s own test suite covers `validate()`'s actual logic directly against synthetic bad fixtures instead — see `internal/hbp/README.md`.
4. **`store.NewFileStore(cfg.DataFilePath)`** — creates the data directory if needed, loads any existing `cases.json`. A failure here (corrupt existing file, permission problem) is also fatal at startup, not discovered on the first request.
5. **`newExtractor(cfg)`** — a four-way switch on `cfg.LLMProvider` (already validated by `config.Load()`) constructing whichever of `extract.NewClaudeClient`/`NewGroqClient`/`NewGeminiClient` is active; the `default` case returning an error rather than assuming the config validation guarantee holds forever. Then `api.Server` and the router are assembled from that plus the file store — see `internal/api/README.md` for why `Server` is built from interfaces here specifically so tests elsewhere can build the equivalent from fakes.
6. **Serve, with graceful shutdown.** `httpServer.ListenAndServe()` runs in a goroutine; `run` blocks on either a server error or `ctx.Done()`. On cancellation, `httpServer.Shutdown(shutdownCtx)` — a package var default of 15 seconds, not a hardcoded literal, specifically so a test can shrink it to make the "shutdown itself times out" branch reachable without needing a genuinely slow in-flight request — gets that long to let in-flight requests finish before the process actually exits. Relevant for the one endpoint that can legitimately take a few seconds (the LLM call in `handleIntake`), so a deploy or restart doesn't cut off a request that was already almost done.

## Explicit HTTP server timeouts, and why they're not the Go defaults

`ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` are all set explicitly rather than left at `http.Server`'s zero-value (unlimited) defaults. An unlimited read/write timeout on a public-facing server is a real, well-known resource-exhaustion risk (a slow or malicious client holding a connection open indefinitely) — setting these explicitly, even generously, closes that off without needing a reverse proxy in front of this binary to do it. (A reverse proxy — Caddy — is still the recommended deployment shape; see `docs/DEPLOYMENT.md`. These timeouts are defense in depth, not a substitute.)

## If you're extending this file

Resist adding real logic here. If you find yourself writing an `if` that makes a decision beyond "did this setup step fail, log and exit," "which signal did we receive," or "which provider is configured," that logic almost certainly belongs in a package under `internal/` instead, where it can be unit-tested without spinning up a real process. `main.go`'s value is in being short enough to read in one sitting and trust by inspection — keep it that way. If you add a real failure path (a new setup step that can error), add a corresponding test in `main_test.go` the way every existing step has one — `run`'s whole point is that it's no longer a "hackathon-stage wiring function" exempt from that.
