# `internal/document`

Renders a `store.CaseRecord` as a single, print-ready PDF — the same content already shown on the case result page (`frontend/app/case/[id]/page.tsx`), packaged as one file a family can download, print, or hand directly to hospital billing staff, attach to a CGRMS complaint, or read from during a call to a NALSA Para Legal Volunteer.

## Why this exists

Before this package, the only way to get any of a case's content out of the browser was `CopyableTextBox` — select, copy, and paste it somewhere yourself. That's a real gap for the actual person this tool is for: mid-crisis, often on a phone, at a hospital desk. "Copy this text" still leaves them needing somewhere to paste it before they have anything to show anyone. A downloadable, printable PDF is something to hand over directly, with no intermediate step.

This does **not** close the "automated CGRMS complaint submission" gap documented in `docs/OPEN_QUESTIONS.md` — the family still submits the draft complaint themselves, through the Ayushman App or whichever channel they choose. What changes is the form the draft takes: a formatted document instead of a text box, which is what actually makes it submission-ready rather than something that first needs retyping somewhere else.

## Files

| File | What it does |
|---|---|
| `winansi.go` | The WinAnsiEncoding table and Adobe Core 14 Helvetica/Helvetica-Bold width metrics, plus `shapeText`/`textWidth` — the one place a Go string becomes PDF-ready bytes with a known width. |
| `pdf.go` | `canvas` — the drawing primitives (`fillRect`, `divider`, `line`) and page/cursor bookkeeping, in plain point coordinates. Knows nothing about PDF's binary format. |
| `serialize.go` | `render()` — turns accumulated pages into actual PDF bytes: objects, content streams, the cross-reference table, the trailer. The only file that knows PDF's object format. |
| `layout.go` | Text wrapping (`wrapWords`, `wrapParagraphs`), the `styledLine`/`blockHeight`/`drawBlock` triple that keeps space-reservation and actual drawing in agreement, and the `box`/`heading`/`paragraph`/`numberedList` helpers built on top. |
| `case_document.go` | `BuildCase` — the public entry point. Composes a `store.CaseRecord` into an actual document: color palette (copied from `frontend/app/globals.css`), tier styles, and the per-section draw functions. |

## Why zero third-party dependencies, and why that was actually feasible here

This mirrors the backend's overall architecture (`../../ARCHITECTURE.md`) — no PDF library, no font-embedding pipeline. That sounds like it should be much harder than it turned out to be, and the reason is worth being explicit about rather than assumed: **this package's actual real-world input uses exactly two non-ASCII characters** — an em dash and the rupee sign (₹) — verified directly by scanning the real generated content, not assumed by reading the source and hoping (`case_document_test.go`'s `TestTemplateTextHasNoUnrenderableCharacters`, which fails loudly if a future template edit introduces a character this package can't render). The em dash has a real glyph in the standard WinAnsiEncoding; the rupee sign doesn't (it wasn't adopted until 2010, decades after the standard 14 fonts' metrics were fixed), and is deliberately substituted with "Rs." rather than solved by embedding a Unicode font. That one substitution is what kept this a "write PDF objects directly" problem instead of a "subset and embed a TrueType font, handle CID mapping, and hope the family's original free-text input never contains a script like Malayalam that would need real shaping (HarfBuzz-style glyph reordering) to render correctly at all" problem. It genuinely might have needed to be the latter — it just turned out it didn't, and that was checked rather than guessed.

One consequence: this package deliberately never renders a family's raw free-text input verbatim. Every field it draws (`CareFirstMessage`, `TierMessage`, `HospitalScript`, `ComplaintText`, evidence notes) is either an `internal/response` template's English output or something a person typed directly into this tool's own evidence form — never, say, the original multilingual description text a family might have entered elsewhere in the flow. That's not a content restriction this package imposes; it's simply what `store.CaseRecord` actually carries, and it's what keeps "exactly two non-ASCII characters, verified" true.

## A real bug this package's own development caught, worth knowing about if you touch `pdf.go` or `layout.go`

The first draft of `fillRect` drew a background rectangle without moving the page cursor, on the assumption that callers would advance past it manually afterward. The very first real usage got that wrong — a heading was drawn starting from inside the rectangle's own footprint, producing visibly overlapping text. It was caught by actually rendering a sample PDF and looking at it (rasterized with `pdftoppm`), not by reading the code. The fix wasn't "remember to advance correctly at each call site" — it was removing the possibility of getting it wrong: `box()` (in `layout.go`) is now the only sanctioned way to draw a filled background behind content, and it always computes the exact required height with `blockHeight` *before* drawing anything, reserves that space with one `ensureSpace` call, and only then draws the rect and the content on top. `fillRect` itself is still exported (package-internally) but its doc comment in `pdf.go` says explicitly that `box` should be the only real caller. If you find yourself calling `fillRect` directly from a new draw function, that's very likely the same mistake trying to happen again.

A second, smaller version of the same class of bug: `numberedList`'s first draft identified "the first wrapped line of this item" as "index 0 of the wrapped-lines slice" — which silently drew no prefix at all for any item whose text happened to start with a literal newline (wrapping such an item produces a blank-gap marker at index 0, not real text, so the `index == 0` check fired on the wrong line and never fired again). Fixed by tracking "have I drawn the prefix yet" explicitly rather than inferring it from position. Neither bug was hypothetical by the time it was found — both were caught by this package's own tests or its own diagnostic rendering, not left for someone else to discover later.

## Testing approach

99%+ statement coverage, but the number is a side effect, not the goal — a few things were deliberately tested beyond what coverage alone would demand, because "the byte-writer's output looks plausible" and "the byte-writer's output is actually a valid PDF" are different claims:

- **`serialize_test.go`** checks PDF structure directly: balanced object/stream markers, and — the property that actually determines whether a PDF opens at all — every cross-reference table offset is independently verified to point at the exact byte where that object's `N 0 obj` header actually starts, computed by parsing this package's own output rather than trusting `render()`'s internal bookkeeping.
- **Independent validation outside Go entirely**, done during development and not (deliberately) part of the committed suite: generated sample PDFs were parsed with Python's `pypdf` (confirming text extraction matches what was drawn, rupee amounts included) and rasterized with `pdftoppm` for direct visual inspection. Not repeatable via `go test`, but real — see this package's git history / the session that introduced it if you want to redo that check after a significant change to `serialize.go`.
- **`layout_test.go`** tests the wrapping/layout engine directly, not just through `case_document_test.go`'s higher-level assertions — including the "single word wider than the page" edge case and the two bugs described above, both of which have regression tests named after them specifically.
- **`case_document_test.go`** builds representative (not minimal) `store.CaseRecord` values for all five outcomes, and separately checks the honest things that are easy to get subtly wrong under time pressure: a zero-value `CreatedAt` doesn't render as a misleading year-0001 date; free-text evidence fields containing PDF's own special characters (parens, backslashes) don't corrupt the document; optional sections are actually absent (not just empty) when their source field is empty.

## If you change `internal/response`'s templates

Run `go test ./internal/document/...` afterward. `TestTemplateTextHasNoUnrenderableCharacters` scans realistic assembled case content (not `internal/response`'s raw Go source) for any character outside `{ASCII, em dash, rupee sign}` and fails immediately if it finds one — that's your signal a new template's wording needs either a plain-ASCII rephrase or a deliberate decision to extend this package's character handling, not a signal to ignore.

## If you're tempted to add Malayalam (or any script beyond WinAnsi's range)

Read `docs/OPEN_QUESTIONS.md`'s note on Malayalam localization first — this project has an existing, deliberate decision not to machine-translate safety-critical template text without native-speaker review, for reasons unrelated to this package. If that ever changes, know that it changes this package's scope substantially: rendering Malayalam correctly needs real text shaping (conjunct formation, glyph reordering), not just "embed a font with the right glyphs in it" — a font with the right glyphs but no shaping engine behind it produces text that *looks* rendered but is actually wrong, which is arguably worse for a document a family hands to someone else than not rendering that text at all. That's a substantially different (and substantially larger) project than this package currently is.
