# `internal/extract`

The one package in this entire backend that calls a language model. Everything before it (`internal/retrieval`) is cheap keyword scoring; everything after it (`internal/tiering`, `internal/response`) is plain, deterministic Go with zero model calls. That boundary is not incidental — it's the spec's own design principle (Section 58: "AI where genuine language ambiguity exists, deterministic auditable logic everywhere after"), and it's what makes `internal/tiering` reach 94.5% test coverage and run fully offline. If you're tempted to add a second model call somewhere downstream of this package, read `../../../ARCHITECTURE.md`'s "why the extraction/tiering boundary is exactly where it is" first.

## Files

| File | What it does |
|---|---|
| `types.go` | The `Extractor` interface, `Result` and its component types (`CandidateMatch`, `ExclusionMatch`, `PendingSignal`), and the trimmed-down `CandidatePackageInfo`/`CandidateExclusionInfo` types actually sent to the model. |
| `prompt.go` | `systemPrompt` (the actual instructions sent to the model — provider-agnostic content, the same text regardless of which client sends it) and `extractMatchToolSchema` (the JSON Schema for structured output, in the standard lowercase-type form Anthropic and Groq both accept directly). |
| `claude_client.go` | `ClaudeClient` — an `Extractor` calling `api.anthropic.com`'s Messages API directly via `net/http`, no SDK. Also home to `buildUserContent`, `toolExtractionPayload`, `validatePayload`, `truncate`, and `parseRetryAfterSeconds` — genuinely shared, not Claude-specific, and used by `groq_client.go`/`gemini_client.go` too (see below). |
| `groq_client.go` | `GroqClient` — an `Extractor` calling Groq's OpenAI-compatible chat completions API. |
| `gemini_client.go` | `GeminiClient` — an `Extractor` calling Google's `generateContent` API, including `convertToGeminiSchema`, since Gemini's structured-output schema format uses uppercase type strings (a genuine wire-format difference, not a stylistic one — see that function's doc comment). |
| `fake_client.go` | `FakeClient` — a deterministic, registered-by-exact-string test double satisfying the same interface, used by every other package's tests. |

## Why `Extractor` is an interface, and why it now has four implementations

`internal/api` depends only on the `Extractor` interface, never on a concrete client type. That's what makes the entire HTTP layer — routing, middleware, request/response handling, the tiering and response logic downstream — testable without a live API key or network access: tests wire up a `FakeClient` with pre-registered responses instead. `FakeClient` matches by **exact input string**, deliberately not fuzzy or "smart" — a fuzzy fake that tries to figure out a plausible response risks masking a real wiring bug (the API handler passing the wrong string through, say) behind a fake that quietly compensates for it. If a test's fake has no registered response for what it was actually asked, it fails loudly (`fmt.Errorf` naming the exact missing description), not silently.

`ClaudeClient`, `GroqClient`, and `GeminiClient` all implement the same interface against three different real APIs — this isn't three unrelated integrations bolted together, it's the same extraction contract (`extractMatchToolSchema`'s fields, `validatePayload`'s rules) enforced against whichever provider `LLM_PROVIDER` selects (see `internal/config` and `cmd/server/main.go`'s `newExtractor`). Concretely, this means:

- **The system prompt (`systemPrompt`) and the schema's *meaning*** — what fields exist, what's required, what each one means — **are identical across all three.** Only the wire format differs: Anthropic gets it via tool-forcing (`tool_choice`), Groq via `response_format: {type: "json_schema"}`, Gemini via `generationConfig.responseSchema`. A family gets the same extraction behavior regardless of which provider is configured, modulo each underlying model's own quality.
- **`validatePayload` is the real safety net, shared unchanged across all three.** A schema — any provider's — constrains what a model's output *should* look like, but doesn't guarantee it in every edge case (an empty `candidates` array despite `minItems: 1`, an out-of-range confidence score, an unrecognized `pending_signal` value). This is especially deliberate for `GroqClient`, which uses `strict: false` rather than Groq's `strict: true` mode — see that file's doc comment for why `validatePayload` paired with non-strict schema-guided generation is the more robust pattern, per Groq's own structured-outputs documentation.
- **Retry/backoff logic is *not* shared code** — each client has its own, structurally identical but independently written. This was a deliberate choice, not an oversight: this codebase's own precedent (`internal/retrieval`'s `scorePackage`/`scoreExclusion`, kept parallel rather than merged) favors a reader being able to understand any one client's `Extract` method top-to-bottom without needing to jump to a shared helper file — see each client's own doc comment for its retry policy (transient failures only, bounded attempts, `Retry-After` honored under a cap).

## `prompt.go`: why the system prompt looks the way it does

`systemPrompt` is a direct encoding of the source spec's Appendix AA ("Prompt and System Design Principles") — each of the seven numbered principles in the prompt text maps 1:1 to a specific line in that appendix, kept that way on purpose so a reviewer can check the prompt against the spec without cross-referencing two documents that have drifted apart. Worth understanding even if you never touch this file:

- **Principle 1 (score at least the top two candidates)** exists because `internal/tiering`'s amber-tier logic depends on the *gap* between the top two confidence scores, not just the top score alone — collapsing to a single best guess here would throw away the exact signal that decision depends on.
- **Principle 2 (bias conservatively)** is the model-level expression of this whole system's "care-first" stance: a false "this is definitely covered" is worse than an unnecessary "let's double-check," so the prompt explicitly asks the model to score close candidates close together rather than resolve genuine uncertainty into false confidence.
- **Structured output, not "please respond in JSON."** Every provider gets a real, enforced schema, not a hopeful instruction — Anthropic via forced tool use, Groq and Gemini via their own native structured-output mechanisms (see each client's file). This is what makes Appendix AA's "never let the model output a tier without a cited reason attached, enforced structurally" actually true rather than aspirational across all three providers, not just the original one.
- **`CandidatePackageInfo`/`CandidateExclusionInfo`, not the full `hbp.Package`/`hbp.Exclusion` structs, go into the prompt.** Internal fields — `ConfidenceNotes` (written for engineers), `Verified`, `SourceNote` — never reach the model, and therefore never have a path to leak into a family-facing response, regardless of which provider is configured. This is enforced by the type system (the trimmed structs simply don't have those fields), not by a convention someone has to remember.

## The real clients: `claude_client.go`, `groq_client.go`, `gemini_client.go`

Plain `net/http` in every one, no provider SDKs — see `../../../ARCHITECTURE.md` on why the whole backend has zero third-party dependencies (a build-environment network constraint that turned out to be a genuine engineering benefit, not just a workaround). A few things worth knowing if you're modifying any of these:

- **`WithHTTPClient`/`WithBaseURL` (and each client's equivalently-named options)** exist purely so tests can point a client at an `httptest.Server` instead of the real API — the production code path and the tested code path are the same code, just pointed at a different URL.
- **Bounded retry with backoff, not "no retry" and not unlimited retry.** Every client retries transient failures only (network errors that aren't context-cancellation, HTTP 429, HTTP 5xx) up to a small fixed number of attempts, honoring a server's `Retry-After` header up to a cap rather than an arbitrarily long one. A bad request or a validation failure fails immediately — retrying an identical request against a server correctly rejecting it can't produce a different outcome, and making a distressed family wait through backoff for a failure that was never going to resolve is worse than failing straight to `internal/api`'s care-first fallback. (An earlier version of this file's docs described this package as having no retry logic at all — that was true once, briefly, and is the kind of claim this project's own culture exists to catch and fix rather than leave stale; see `docs/TESTING.md` for exactly which tests cover which retry path today.)
- **`validatePayload`** is the shared safety net described above — one function, in `claude_client.go`, used by all three real clients.

## `MaxTokens`/`MaxCompletionTokens`/`MaxOutputTokens`, and why the model is configurable but small by default

The task here is bounded classification over a short, pre-filtered candidate list (at most 20, from `internal/retrieval`) — not open-ended generation. It doesn't need a large model to do well, and this system's entire per-query cost is dominated by this one call (see `../../../ARCHITECTURE.md`'s cost breakdown), so every provider's default model is deliberately a small, cheap one — see `.env.example` for the current default and reasoning for each of the three (`CLAUDE_MODEL`, `GROQ_MODEL`, `GEMINI_MODEL`, all read via `internal/config`). Switching providers, or switching models within a provider, is an env var change, not a code change.

## If you're extending this package

- **Changing the prompt**: keep the Appendix AA principle-numbering correspondence intact, or update the comment that describes it — the whole point of that structure is that a reviewer can check the prompt against the spec directly. Since `systemPrompt` is shared verbatim across all three providers, one edit covers all of them — no need to touch `groq_client.go` or `gemini_client.go` for a prompt-wording change.
- **Adding a new field to `Result`**: update `extractMatchToolSchema` (Anthropic and Groq both read this directly; Gemini's `geminiExtractSchema` derives from it automatically via `convertToGeminiSchema`, so it doesn't need a separate edit), `toolExtractionPayload` (shared, in `claude_client.go` — all three clients unmarshal into this same type), and `FakeClient`'s test fixtures wherever they construct a `Result`. Three places to touch, not the four you might expect, precisely because the schema and payload type are genuinely shared rather than duplicated per provider.
- **Adding a fourth provider**: look at `groq_client.go` first, not `claude_client.go` — Groq's OpenAI-compatible wire format is the more common shape a new provider is likely to share, and `buildUserContent`/`toolExtractionPayload`/`validatePayload`/`parseRetryAfterSeconds` are all already factored out for reuse. Then wire it into `internal/config`'s `validLLMProviders` map and `cmd/server/main.go`'s `newExtractor`.
- **This file is part of the codebase's documentation convention** — see the repo root `README.md`. Keep it in sync with the code, in the same change. (See the retry-logic correction above for what happens when that doesn't happen.)
